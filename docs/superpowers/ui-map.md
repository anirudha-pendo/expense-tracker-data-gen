# UI Map — Expense Tracker (for Playwright automation)

Generated by reading actual component source (not guessed).

Stack facts that affect selector strategy:
- `react-hook-form@7` + `zod@4` (`@hookform/resolvers/zod`) for most forms — these fields are **RHF-registered** (`register(...)`), so Playwright `locator.fill()` works correctly (it dispatches real input events RHF listens to). Do **not** set `.value` via `evaluate()`.
- Radix primitives via the `radix-ui` package, wrapped in local shadcn-style components under `src/components/ui/*`. Every wrapper stamps a `data-slot="..."` attribute (e.g. `data-slot="dialog-content"`, `"select-trigger"`, `"button"`, `"input"`, `"switch"`, `"tabs-trigger"`, `"alert-dialog-content"`). These are **shared across every instance of that primitive app-wide** — useful for scoping ("wait for `[data-slot=dialog-content]` to appear/disappear") but never unique on their own.
- **No `data-testid` attributes exist anywhere in the app** (`grep -rn "data-testid" src` → zero results).
- Toasts are `sonner`, mounted once in `src/app/providers.tsx`: `<Toaster richColors position="top-right" />`.
- Radix `Select` components in this app are **not native `<select>` elements** — they render a button trigger plus a portaled listbox. Never use `selectOption()`; click the trigger, then click the option by its `role="option"` accessible name in the (portaled, appended to `<body>`) listbox.

## 2. `src/features/auth/` — Sign-in / Sign-up

### Zod schemas (`src/features/auth/schemas/auth.schema.ts`)

```ts
signUpSchema = {
  username: string, min 3, max 30, regex /^[a-zA-Z0-9_]+$/ ("letters, numbers, and underscores")
  email: z.email("Enter a valid email address")   // zod 4 top-level API, not z.string().email()
  displayName: string, min 1, max 50
  password: string, min 8   // no upper/lower/digit/symbol requirement — length only
  confirmPassword: string   // .refine: must equal password, error path -> confirmPassword
}

signInSchema = {
  email: z.email("Enter a valid email address")   // NOT username — email is the login identifier
  password: string, min 1
}
```

**Email is the login.** `signIn(email, password)` looks the user up through the
`by-email` index; username is still collected at sign-up, still unique, still
shown on the profile — it just is not what you sign in with.

Business-rule errors (not from zod, thrown by `useAuth` and surfaced via `toast.error`):
- Sign up with an existing username → `Error("Username is already taken")`
- Sign up with an existing email → `Error("Email is already registered")`
- Sign in with wrong email/password → `Error("Invalid email or password")` (**deliberately the same message for both an unknown account and a wrong password** — never split it, it would leak which emails are registered)

**Valid input generator guidance:** username 3–30 chars, `[A-Za-z0-9_]` only; email any address zod accepts (dots fine, unlike the username); displayName 1–50 chars any text; password >= 8 chars (e.g. `Password123`); confirmPassword must equal password exactly.

|---|---|---|---|
| Email | `<Input type="email">` | `id="email"`, `placeholder="you@email.com"`, `autoComplete="email"`, label "Email" (`htmlFor="email"`) | Yes — `register("email")`, use `.fill()` |
| Password | `<Input>` | `id="password"`, `placeholder="••••••••"`, `autoComplete="current-password"`, label "Password" | Yes — `register("password")`, use `.fill()` |

Field errors render as `<p class="text-destructive">` with the exact zod message directly under the field.

### Sign-up form (`components/sign-up-form.tsx`) — 8 interactive elements

Field order top to bottom: Display Name, Username, Email, Password, Confirm Password.

| Element | Type | Handle | RHF? |
|---|---|---|---|
| Display Name | `<Input>` | `id="displayName"`, `placeholder="Jane Doe"`, `autoComplete="name"` | Yes, `.fill()` |
| Username | `<Input>` | `id="username"`, `placeholder="jane_doe"`, `autoComplete="username"` | Yes, `.fill()` |
| Email | `<Input type="email">` | `id="email"`, `placeholder="jane.doe@email.com"`, `autoComplete="email"` | Yes, `.fill()` |

| Show/hide toggle | `<button>` | `aria-label="Show password"` / `"Hide password"` | n/a |

| Submit | `<Button type="submit">` | Text **"Create account"** | n/a |
| "Sign in" link | `<Link to="/sign-in">` | Text "Sign in" | n/a |

**Toasts:** sign-in failure → `toast.error(message)`, fallback `"Sign in failed"`. Sign-up failure → fallback `"Sign up failed"`.

**Post-submit navigation:** successful sign-in → `navigate(hasWorkspace ? "/" : "/setup-workspace")`. Successful sign-up → always `navigate("/setup-workspace")`.

**Both `id="email"` inputs are `type="email"`.** The browser's own validation therefore runs before zod's; it is the looser of the two, so anything zod accepts submits fine.

## 10. `src/features/quick-add/` — Quick Add command palette

### How it's opened
1. **Keyboard shortcut**: `Cmd+K` / `Ctrl+K` — global `keydown` listener in `AppLayout`, so it only works on pages rendering `AppLayout` (Dashboard, Transactions, Insights, Goals, Settings — **not** sign-in/sign-up/workspace-setup). Pressing it while **another** dialog is open (`[data-slot="dialog-content"]` or `[data-slot="alert-dialog-content"]` present) is **ignored**. **Close any other open dialog first.**
2. **Button click**: every page header renders `<button aria-label="Open quick add">`. **Use this `aria-label` — the visible text varies by OS and viewport.**

### Dialog behaviour (`components/quick-add-palette.tsx`)
- Radix `Dialog` with `showCloseButton={false}` — **no visible X close button**.
- `DialogHeader` is `sr-only`: title **"Quick Add"**, description "Type a transaction in plain language, e.g. coffee 4.50 yesterday".
- Main input: `aria-label="Quick add transaction"`, placeholder `Try "coffee 4.50 yesterday" or "salary 3000 income june 1"`. Plain `useState` — `.fill()` works.
- **There is no Save/Submit button.** **Enter** submits, but only if `canSave` (`parsed.amount !== null && effectiveCategory !== null`). If not, Enter does nothing silently.
- Footer hint is misleading: shows **"include an amount to save"** even when the real blocker is an unresolved category. Do not use it as a save-readiness signal.
- Category override chips: one `<button type="button">` per matching category, visible text = category name, no id/aria-label — select by exact text within the open dialog.
- The dialog **does not close on save** — the input clears and it stays open. Close with `Escape`, overlay click, or the shortcut again.
- Toast on save: `` `Added: {description}` `` or `"Failed to add transaction"`.

### Parser (`lib/parser.ts`)
Deterministic token parser: strips an explicit `income`/`expense` keyword, then a date phrase (`today`, `yesterday`, `N days ago`, weekday names, `M/d[/yyyy]`, `yyyy-MM-dd`, `Month d` / `d Month`), then a numeric amount (prefers `$`-prefixed or decimal, else the last bare number); remaining tokens are the description; category is inferred from description keywords + history. **To reliably produce a savable entry, include a number and use words matching default categories** (e.g. "salary", "coffee", "grocery"), or click a category override chip.

## Cross-cutting reference

### `data-testid` audit
**None exist anywhere.** Build selectors from labels (`getByLabel`), roles + accessible names (`getByRole`), placeholders (`getByPlaceholder`), visible text (`getByText`), and the radix `data-slot` attributes for scoping open dialogs/menus (never for uniqueness).

### All confirmation dialogs (AlertDialog) — exact button text
| Where | Title | Cancel | Confirm |
|---|---|---|---|
| Delete a transaction | "Delete transaction?" | "Cancel" | "Delete" |
| Delete a goal | "Delete goal?" | "Cancel" | "Delete" |
| Delete a category | "Delete category?" | "Cancel" | "Delete" |

These 3 are the **only** `AlertDialog` usages in the app. Clicking outside or Escape also dismisses (equivalent to Cancel).

### Toasts
Sonner, portaled top-right, NOT dialogs, auto-dismiss. Assert promptly after the triggering action.

### Ambiguous / hard-to-automate labels — always scope by container
- **"Delete"** — transaction row dropdown item, goal-card icon (`sr-only` "Delete goal"), category row icon (`sr-only` "Delete"), and the confirm button in all 3 AlertDialogs. Never use a bare page-level `getByRole('button', { name: 'Delete' })`.
- **"Edit"** — transaction dropdown "Edit" vs goal-card `sr-only` "Edit goal" vs category row `sr-only` "Edit".
- **"Save changes"** — Profile form, Workspace settings form, and Transaction/Goal edit dialogs. Category dialog says just **"Save"**.
- **"Cancel"** — reused by every dialog. Always scope to the currently-open dialog.
- Categories with `scope: "both"` render **twice** with identical Edit/Delete buttons.
- `Add money` / goal Edit / goal Delete repeat per `GoalCard` with identical text — scope by the card containing the goal's name.
- `BudgetManager`'s "Set" button is identical across every row.
- Quick Add has **no submit button** (Enter only) and its blocker hint text is misleading.
- The transaction attachment file input has **no `id`** (unlike `#import-file`) — use `input[type="file"]` scoped to the open dialog.
- PDF attachments open in a **new tab**; images open a dialog.
- Export JSON/CSV trigger real downloads — need `page.waitForEvent('download')`.
